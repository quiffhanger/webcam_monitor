# K95 G-keys and lighting

`k95_gkeys.py` runs with webcam_monitor. It reads only the K95 RGB Platinum
(USB 1B1C:1B2D) vendor G-key input, translating G1-G6 into complete
Ctrl+Shift+Alt+top-row-1 through 6 shortcuts for the existing AHK scripts.
It does not edit persistent profiles or change key routing. OpenRGB still
performs the existing 139-LED updates. No iCUE installation is required.

## Recovery

- Normal tray exit, monitor-thread exceptions, and Python exit request hardware mode.
- A separate hidden guardian watches the actual owner process handle and a
  one-second heartbeat. Owner termination, pipe closure, or eight seconds
  without a heartbeat cause recovery even when Python exit handlers cannot run.
- The guardian owns and serializes OpenRGB updates. Updates have a 12-second
  timeout. A Windows kill-on-close job contains each lighting process, assigned
  before its first instruction runs, preventing orphan lighting writes if the
  guardian itself dies. The owner attempts hardware recovery on guardian loss.
- Recovery stops lighting first, sends the hardware-mode command twice, then
  reads the mode back. It retries transient failures. The original stored
  hardware macros are left intact.
- A named mutex prevents two managed keyboard controllers running together.
  Failure to establish input/recovery disables lighting, leaving other monitor
  functions available. Input disconnect also disables lighting; restart the
  monitor after reconnecting to resume software lighting.

This cannot guarantee recovery if Windows terminates both processes together,
during power loss, or if the keyboard/USB connection stops responding. After
an unresponsive-device failure, unplug/replug the keyboard. Do not separately
run OpenRGB or another keyboard controller alongside the daemon.

## Logs and testing

`webcam_monitor.log` records only G-key numbers, never normal typed text.
`k95_recovery.log` records confirmed hardware restoration; `k95_openrgb.log`
records lighting-tool output. G4 has no known AHK action but still emits its chord.
Windows may reject injected shortcuts into an elevated target from a normal
user process; the bridge reports rejected injections and restores hardware mode.

On LAPTOP-8REHJR1B, 2026-09-09: seven offline tests passed. Live tests verified
software mode 2 before normal exit, forced owner termination, forced
guardian termination, and suspension of the actual owner process (heartbeat
timeout); each returned to read-back hardware mode 1. Physical
G1-G6/AHK behavior with lighting remains pending user confirmation.
The user subsequently confirmed G-key actions with lighting, and again after
forced termination of the live daemon and verified hardware recovery.

After a later unexplained lighting shutdown, `monitor_diagnostics.log` was
added for file-only exception and lifecycle reporting, independent of Tk and
console logging. It captures monitor, thread, Tk callback, and background-task
exceptions, redacts URLs, and rotates at 1 MB with two backups. The recovery
log now distinguishes owner exit, pipe closure, explicit STOP, timeout, and
guardian errors. A restart does not by itself establish the original cause.
